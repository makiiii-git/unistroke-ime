# tools/

オンデバイス変換（`OnDeviceConverter`）が使うバイナリ辞書を作るためのツール。

## 生成手順

```sh
# 1. Mozc の OSS データを取得して辞書をビルドする（初回のみ 60 MB ほどダウンロード）
python3 tools/build_dictionary.py --fetch

# 2. 検証
python3 test_dictionary.py     # バイナリの整合（件数・サイズ・ソート順・往復）
python3 test_ondevice.py       # 変換品質のスモークテスト
```

生成物は `app/src/main/assets/ondevice.dic`。
`--fetch` は `tools/mozc-src/` に元データを落として再利用する（2 回目以降は再取得しない）。
`tools/mozc-src/` は生成物ではなく素材なのでコミットしない。

主なオプション。

| オプション | 既定 | 意味 |
| --- | --- | --- |
| `--src DIR` | `tools/mozc-src` | Mozc の `dictionary_oss` を置いたディレクトリ |
| `--out FILE` | `app/src/main/assets/ondevice.dic` | 出力先 |
| `--limit N` | 240000 | 残す語数の上限。サイズはほぼこれに比例する |
| `--fetch` | — | 足りないファイルを GitHub から落とす |

## 元データ

すべて [google/mozc](https://github.com/google/mozc) の `src/data/dictionary_oss/`
（**BSD-3-Clause**）。

| ファイル | 中身 |
| --- | --- |
| `dictionary00.txt` … `dictionary09.txt` | 読み / 左文脈ID / 右文脈ID / コスト / 表記 の TSV。約 129 万行 |
| `id.def` | 文脈ID（0〜2671）→ 品詞文字列 |
| `connection_single_column.txt` | 2672 x 2672 の接続コスト行列（36 MB のテキスト） |

BSD-3-Clause はバイナリ再配布時に著作権表示と免責事項を「ドキュメント等に含めること」を
求めるので、アプリの 設定 → ライセンス（`LicenseActivity`）でライセンス全文を表示している。
辞書を差し替えるときはこの表示も合わせて見直すこと。

Mozc UT など **CC BY-SA の辞書は使っていない**（配布形態に制約が乗るため）。
`dictionary_oss` は帰属表示だけで足りる。

## トリミングの方針

129 万エントリをそのまま積むと数十 MB になるので、`--limit` 件まで削る。
残す優先度は「Mozc のコスト＋品詞ごとの下駄」で決める。

- 助詞・助動詞・接続詞・連体詞は数が少なく必須なので、強い下駄（-20000 など）で必ず残す
- 固有名詞（人名・地名・組織名）は 43 万件と最多だが日常入力での出番が少ないので重く削る
- 1 文字の読みはラティスを膨らませるうえに誤変換の元なので、自立語は特に厳しく削る
- ひらがな読みでない語（カタカナ読み・英数字混じり）は最初から対象外
- 1 つの読みにつき最大 6 表記まで

さらに保存コストそのものを調整している。

- カタカナ表記に +900。Mozc には「です→デス」「いい→イイ」がコスト 0 で入っていて、
  素直に使うと平文がカタカナだらけになる
- 読みと表記が同じ（ひらがなのまま）の**自立語**に +1200。
  「わたし」がコスト 0 で入っていて「私」に勝ってしまうのを防ぐ。
  助詞・助動詞・感動詞は「は」「を」「です」「ありがとう」が正解なので触らない

## 接続コストの畳み込み

接続行列は 2672² = 714 万要素あり、int16 でも 14 MB になって端末に載せられない。
そこで `id.def` の品詞文字列のうち **活用型（五段・カ行 など）と語そのものを落とした
5 フィールド**で文脈IDをまとめ、**187 の品詞グループ**へ畳む。
残すフィールドは 品詞 / 細分類1 / 細分類2 / 細分類3 / **活用形**。
活用形（連用形・基本形など）は「連用形のあとに助動詞が来る」といった判断に効くので必ず残す。

グループ対の代表値は `min + 0.25 * (mean - min)`。

- 純粋な `min` は「そのグループ対が成立する最良のケース」なので楽観的すぎ、
  1 文字漢字の誤変換（「てい」→「低」など）を止められない
- 純粋な `mean` はグループ内の外れ値に引きずられて正しい接続まで高くなる
- 20 文のスモークテストでは 0.25 前後が最も良かった

結果は 187² x 2 = 約 68 KB。`α` を変えるときは `test_ondevice.py` を回して確認すること。

グループ数を 585（活用型も残す）まで増やす案も試したが、
グループあたりの標本が減って `min` がより楽観的になり、
サイズが 0.7 MB 増えたうえで品質は落ちた（8/20 → 4〜5/20）。

## バイナリ形式

リトルエンディアン。読み取り側は `OnDeviceDictionary.kt`（Kotlin・メモリマップ）と
`ondevice_model.py`（Python・検証用）の 2 つがあり、常に同じ結果を返す。

```
 0  char[8]  magic "UNIDIC2\0"
 8  u32      keyCount        読み（鍵）の種類数
12  u32      wordCount       語数
16  u32      keyIndexOff
20  u32      keyBlobOff
24  u32      keyBlobLen
28  u32      wordArrayOff
32  u32      surfaceBlobOff
36  u32      surfaceBlobLen
40  u32      maxKeyChars     最長の読みの文字数
44  u32      alphabetOff
48  u32      groupCount      品詞グループ数
52  u32      groupTableOff
56  u32      matrixOff
60  u32      bosGroup        BOS/EOS のグループ番号
64  u32      formatVersion
68  ...      予約（0 埋め、ヘッダは 80 バイト固定）

鍵インデックス  (keyCount + 1) * 8
    u32 鍵ブロブ内オフセット / u32 語の開始番号
    末尾は番兵。読みの長さも語の数も次エントリとの差分で求める

鍵ブロブ        読みを 1 文字 1 バイトへ符号化して連結（区切りなし）

語配列          (wordCount + 1) * 10
    u32 表記ブロブ内オフセット / u16 コスト / u16 左グループ / u16 右グループ
    末尾は番兵。表記の長さは次エントリとの差分

表記ブロブ      UTF-8 の表記を連結

字母表          u16 個数 + 個数 * u16 コードポイント

グループ表      groupCount * 2   u8 品詞クラス / u8 フラグ

接続行列        groupCount^2 * 2 (i16)
    matrix[左語の右グループ][右語の左グループ]
```

読みの符号化は「ひらがな + ー + ゝゞ」の 89 文字を **コードポイント昇順に 1 始まりの
1 バイト**へ割り当てたもの。昇順に割り当てているので、**符号化バイト列の辞書順が
そのまま読みの文字列順**になり、鍵インデックスをそのまま二分探索できる。
1 文字 1 バイトなので鍵ブロブは UTF-8 の 1/3 で済む（約 0.9 MB）。

共通接頭辞検索は「範囲を 1 バイトずつ狭める」方式。深くなるほど探索範囲が小さくなり、
空になった時点で打ち切れるので、20 文字の読み全体でも数百回の比較で終わる。

## APK での扱い

`app/build.gradle.kts` の `androidResources { noCompress += "dic" }` で無圧縮にしている。
これが無いと `AssetManager.openFd()` が使えず、メモリマップできない
（＝起動時に 7 MB を展開してヒープに載せることになる）。
拡張子を変えるときは必ずこの設定も直すこと。

## 認識器の人間モデルについて（検証ハーネス）

`stroke_sim.py` の手ぶれは **低周波の相関ノイズ**（`_correlated_jitter`）で作る。
各サンプルへ独立なガウスノイズを載せる方式から乗り換えた。

独立ノイズだと、点が密なほど軌跡が細かくジグザグし、**軌跡長が実際の 2〜3 倍**に膨らむ。
その結果

- 「直線らしさ」（始点終点の距離 / 軌跡長）が、まっすぐな `i` でも 0.15 まで落ちる
- 「総回転角」は、曲線の `e`（645〜1175 度）より直線の `i`（1071〜2657 度）のほうが**大きくなる**

という具合に、軌跡長や方向変化を使う統計がすべて反転・崩壊する。
実際の指の震えは相関を持つので、少数の制御点でずれを作って補間するほうが実機に近い。

このモデルに替えた時点で「雑に書いた」プロファイルは素直に難しくなったため、
`test_recognition.py` の合格ラインは実測に合わせて引き直してある
（1 本も間違えないことを求めるのではなく、率とマージン中央値で見る）。

## 認識器の「形の性質」によるゲート

コサイン類似度だけでは、**形として明らかに別物**の候補が高スコアで競り勝つことがある。
実機ログで見つかった例:

- 縦長・幅狭の ε が `i`（直線）に 0.95 で一致する（線分の大半が下向きになるため）
- 上弧の浅い ε が `f` に 0.99 で一致する

方向ベクトル列の内積は曲率の違いに鈍感なので、**形そのものの性質**で先に候補を絞る。

| ゲート | 指標 | 効果 |
| --- | --- | --- |
| 直線ゲート | 直線らしさ = 始点終点距離 / 軌跡長。0.76 未満なら `LINE_SYMBOLS`（i, 1, スペース, バックスペース, リターン, シフト, ＼, ／）を候補から外す | 縦長 ε の認識 50% -> 99% |
| 折り返しゲート | 横方向の折り返し回数。テンプレートより 2 回以上多ければ `SIMPLE_SYMBOLS`（c, f, l, t）を候補から外す | ε のマージン中央値 +0.07 -> +0.31 |

どちらも実測で決めた設計上の要点がある。

- **総回転角は使えない**。手ぶれで方向が細かく振れるため、直線 `i`（1071〜2657度）のほうが
  曲線 `e`（645〜1175度）より大きくなり、大小が逆転する。始点終点距離のような
  **大域的な量**でないと手ぶれに耐えない
- **折り返しゲートは全字形に効かせてはいけない**。雑に書いた `h` や「細く下ろして戻す」記号
  （# : |）は折り返し回数が増えるので、自分自身の字形を除外してしまう（実測で最大 10%）。
  過度に吸い込む数種類（c, f, l, t）に絞ると副作用がゼロになる
- **折り返しゲートは直線ストロークに使わない**。斜めに倒れた縦線は横幅を持つため、
  手ぶれで折り返し回数がいくらでも増える。そちらは直線ゲートの担当
- **細長い曲線の非一様スケールには下限が要る**（`ASPECT_FLOOR`）。
  「細く下ろして戻す」記号まで引き伸ばすと幅方向のノイズが増幅され、
  Punctuation の認識率が 99.6% -> 92.7% まで落ちる

### 折り返しゲートの許容差は字形ごとに決める

`REVERSAL_GATE` は「対象の字形 -> 許容差」の対応表。既定は 2 だが、**z だけ 1** にしてある。

z と ε は折り返し回数が 2 対 3 で、差が 1 しかない。既定の許容差 2 では切れないが、
z の折り返し回数は実測で **746/750 がちょうど 2 回、3 回に達したものは 1 本も無い**ため、
許容差 1 で切っても自分自身は落ちない（自己除外 0/750）。これで ε の 91% が z を候補から外せる。
他の字形（c/f/j/l/t/y）は数え違いの幅があるので既定の 2 のまま。

なお z と ε は「**角の鋭さ**」では分離できない。仮説は「z の角は鋭く ε の折返しは丸い」だったが、
実測は逆で、ε のほうが鋭く曲がる（最大局所回転角 p90: z 124 度 / ε 146 度）。
ε は折返しが 3 箇所あるぶん鋭角の数も多く（ε の 63% が 3 個以上、z は常に 2 個）、
「鋭角 N 個以上を z の条件にする」ゲートは、z を通す閾値では ε の 80% も通してしまう。

### 3 つめのゲート: 弦からの「横揺れ」

実機で「e が i になる」報告が続いた。原因は **e の書き方が人によって別字形**だったこと。
ギリシャ文字 ε（弧 → 折返し → 弧）ではなく、**「〜」を縦長に引き延ばした波**で書く人がいる。

この波は幅が狭く縦に長いので、始点と終点の距離が軌跡長に近く、
**直線らしさが 0.88 前後**になって直線ゲート（0.76）を素通りし、i と competing してしまう。
折り返し回数ゲートは対象が c/f/j/l/t/y/z に限られていて i には効かない
（過去に直線系へ適用したら、傾いた縦線が手ぶれで折り返しを持ち i/#shift が落ちた）。

そこで **弦からの符号付き垂直偏差**を使う。始点と終点を結ぶ弦を基準に各点の横方向のずれを測り、
ストロークの大きさの `SWING_DEADBAND`（0.06）を超えたときだけ「振れ」と数え、
符号が 2 回以上反転したら直線系を候補から外す。不感帯があるので手ぶれの微小往復は数えない。

| 不感帯 | 直線系の自己除外率 | 波形 e の認識 |
| --- | --- | --- |
| 0.05 | 0.67% | 82% |
| **0.06** | **0.33%** | **77%** |
| 0.07 | 0.17% | 73% |

直線系の**認識率**への影響はどの値でも測定限界以下だったが、0.05 では #shift が 1 ポイント
落ちたので 0.06 を採用（最終実装での自己除外は i / 1 / #shift / #space / #backspace /
#return / #ext / #ext_slash すべて **0/320**）。

**ゲートだけでは直らなかった**点が重要。i を候補から外しても、波形 e は ε テンプレートと
形が違うので h / s / z に流れるだけだった。**波形の e バリアント 3 種**（1 周期・1.5 周期・
2 周期）を足して初めて直った。

| | 波形 e の認識 |
| --- | --- |
| 対策前 | 0%（全部 i） |
| 横揺れゲートのみ | 0% |
| 波バリアントのみ | 61% |
| **両方** | **77%** |

振幅の小さい波（直線に最も近い）はバリアントに入れていない。入れると i を 6 ポイント食う。
そのぶん、ごく浅い波は今も i に流れる（約 20%）が、これは幾何学的にほぼ直線なので原理的な限界。

### i と #return は分離できない

ユーザーは i を「若干 右上 → 左下」に傾けて書く。ところが **#return はまさに同じ方向の斜線**
（垂直から 47 度）。実測すると、傾き 10 度の時点で #return のスコアが 1.000 に達し、
勝者が傾きに対して単調にならない（10 度 → #return、15 度 → i、18 度 → #return）。

| 傾き | i | #return | 勝者 |
| --- | --- | --- | --- |
| 0 度 | 1.000 | 0.863 | i |
| 5 度 | 0.999 | 0.904 | i |
| 10 度 | 0.999 | 1.000 | #return |
| 15 度 | 1.000 | 1.000 | i |
| 20 度 | 0.996 | 1.000 | #return |

安全に分離できる境界は **8 度程度まで**しかなく、そこから先は数値的に縮退している。
i に傾きバリアントを足すと #return（確定・改行という破壊的な操作）を食う危険が大きいので、
**傾きバリアントは採用しない**。i は縦に近く書くか、書き方トレーニングで個人テンプレートを
登録するのが現実的な解。
